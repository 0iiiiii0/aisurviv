# V260.11 Mobile In-Game HUD Fix

## Scope

V260.11 is based on V260.10 and changes only mobile/touch **in-game HUD layout**. It does not modify gameplay state, networking, server matchmaking, AI, zombie logic, extraction rules, physics, account/session logic, or touch input behavior.

Changed runtime files:

- `client/css/mobile-hud-v26011.css` (new)
- `client/dist/css/mobile-hud-v26011.css` (new; byte-identical to source CSS)
- `client/index.html` (adds the new stylesheet)
- `client/dist/index.html` (adds the new production stylesheet)

The source and production CSS files have the same SHA256:

`d5c94f8150a29fed5d2921d3820d54451e3aacd8e8883f9c09baef0ea0c0c0d5`

## What was fixed

The layout follows the original Surviv mobile strategy: retain the existing `UiLayout.Sm`/touch/orientation system, but give post-upstream/custom HUD elements explicit small-screen geometry.

- Extraction and zombie mission banners are constrained to the safe viewport and layered below original top-center/spectator status.
- Zombie mission HUD no longer relies on a fixed desktop-width minimum on phones.
- Sandevistan mobile action is resized/repositioned to avoid the equipped-ammo HUD and right aim-pad region, including 320x568-class short portrait screens.
- Spectator controls become a compact touch-target layout in landscape; chat/inbox are bounded by the safe viewport.
- Aim-training HUD/actions respect safe-area and mobile touch target sizing.
- The upstream top-center `100vw + padding` horizontal overflow is removed with `box-sizing: border-box` on small UI.
- iPhone safe-area insets are respected where these custom HUDs touch screen edges.
- Mobile CSS is deliberately scoped. `pointer: coarse` rules are capped at 1024 px to avoid changing large touchscreen laptops/desktops; ultra-short-landscape rules are also capped at 1024 px.

## Full regression sweep

The project test inventory was enumerated from `server/package.json`. The aggregate `test:v41-suite` command is only a wrapper around tests already present elsewhere. The non-aggregate commands map to **148 unique TypeScript smoke-test files**, which were individually covered during the regression sweep.

Outcome categories:

- **143 functional test files passed directly.**
- **4 historical source-text assertion tests fail identically on untouched V260.10 and V260.11**, so they are not regressions from this change:
  - `v41LauncherSmokeTest.ts` expects an old PowerShell launcher string.
  - `v50UnifiedTargetDuelAdminSmokeTest.ts` expects an old admin-JS source expression.
  - `v53MatchmakingRecoverySmokeTest.ts` expects an old source expression for room creation.
  - `puzzleDoorSmokeTest.ts` still expects `protocolVersion: 89`.
- `lootNerfSmokeTest.ts` is a randomized statistical threshold test and can alternate pass/fail between runs. V260.11 contains **no server code change**: `server/src`, production `server/dist/server/src`, and `shared` are byte-for-byte identical to V260.10. The test runs entirely on server code and therefore its random threshold fluctuation cannot be caused by this CSS-only HUD change.

## Residual risk

No automated suite can prove the absence of every device-specific browser issue. The main residual risk is physical iOS Safari / Android browser chrome, keyboard, notch, and OS-level touch behavior that a Chromium simulation cannot reproduce exactly. For that reason the implementation avoids changes to input/gameplay code and limits itself to CSS layout with safe-area handling.
